## 1. 무엇을 만들었나 — 기능 분석

한 줄 요약: **외부 장소 API(카카오 로컬)를 좌표 격자로 훑어 대량의 장소를 우리 DB에 채워 넣는 배치 수집기.**

동작을 데이터 흐름으로 보면:

```
전국 bounding box
  → 0.5° rect 격자 셀로 분할
    → 각 셀 × 카테고리(AT4/FD6/CE7/AD5/CT1)로 카카오 category 검색 (page 1~3)
      → 45건 상한에 걸린 셀은 4분할 재귀(quadtree)
        → 응답 장소를 Attraction으로 변환 (주소→지역코드 매핑)
          → 500건 버퍼가 차면 insertAll 업서트 (source='KAKAO')
```

핵심 설계 판단 4가지:

1. **기존 TourAPI 수집 구조를 미러링**했다. `client`(호출) / `service`(순회·적재) / 쿼터 리미터 /
   관리자 컨트롤러로 나뉜 뼈대를 그대로 따르고, 카카오가 실제로 다른 부분만 새로 짰다.
   → *새 구조를 발명하지 않고 검증된 구조에 얹는 것*이 가장 큰 리스크 절감이었다.
2. **좌표 rect + quadtree 세분화**. 카카오는 지역명 검색보다 사각형 검색이 강하고 rect당 45건으로
   잘리므로, 밀집 지역은 셀을 잘게 쪼개 누락을 줄였다.
3. **업서트(UPSERT) 기반 idempotency**. 격자가 겹쳐 같은 장소가 여러 번 잡혀도
   `UNIQUE(source, external_id)` 충돌 시 UPDATE로 흡수 → 재실행이 안전하다.
4. **출처 구분 컬럼(`source`)으로 한 테이블 공유**. 별도 테이블을 만들지 않고 기존 `attraction`에
   TourAPI·카카오를 함께 담아 조회·검색 로직을 그대로 재사용했다.

## 2. 사용한 기술 — 기술 분석

| 영역 | 사용 기술 / 패턴 | 이 프로젝트에서의 역할 |
|---|---|---|
| HTTP 호출 | Spring `RestClient` | 카카오 REST API 동기 호출. 헤더 인증 전용 인스턴스를 별도 구성 |
| 인증 | `Authorization: KakaoAK {key}` 헤더 | 쿼리파라미터 방식(TourAPI)과 대비되는 헤더 토큰 방식 |
| 응답 파싱 | Jackson `JsonNode`(트리 모델) | 스키마가 유동적인 외부 JSON을 방어적으로 읽기 |
| 대량 적재 | MyBatis `<foreach>` 멀티로우 INSERT + `ON DUPLICATE KEY UPDATE` | 한 번의 SQL로 N건 업서트 |
| 멱등성 | 복합 `UNIQUE` 제약 + UPSERT | 재실행/중복 수집 안전 |
| 커버리지 알고리즘 | 격자 순회 + **quadtree**(공간 재귀 분할) | API의 결과 상한을 우회해 밀집 지역까지 커버 |
| 쿼터 관리 | DB(`system_config`) 카운터 + `synchronized` | 일일 호출 한도 추적·차단 |
| 지오/행정구역 | 주소 문자열 파싱 → 행정구역 코드 매핑 | 외부 표기(축약형)와 내부 코드 체계의 정합 |
| 권한 | Spring Security `hasRole("ADMIN")` (URL 기반) | 관리자 전용 수집 트리거 |
| 오류 응답 | `ResponseStatusException` + `@RestControllerAdvice` | 계층 넘어 일관된 에러 응답 |

## 3. 앞으로 이 기술을 쓰려면 공부해야 할 개념

각 항목은 **왜 이게 중요한지 → 무엇을 찾아봐야 하는지** 순서다.

### 3.1 외부 API 연동의 기본기
- **REST 인증 방식의 종류**: 쿼리파라미터 키 · 헤더 토큰(Bearer/커스텀) · OAuth2.
  이번에 TourAPI(쿼리)와 카카오(헤더)를 둘 다 다뤘다. → *API 문서에서 "인증" 항목을 가장 먼저 읽는 습관.*
- **Rate limit / quota**: 429 응답, 일일·초당 한도, 백오프(backoff)·재시도 정책.
  → 검색어: `exponential backoff`, `429 Too Many Requests`, `token bucket`.
- **응답 스키마의 불안정성**: 외부 API는 필드 누락·타입 흔들림(빈 문자열 `""` vs 객체 vs 배열)이 흔하다.
  DTO 바인딩이 깨질 때 트리 모델(`JsonNode`)로 방어하는 법. → `Jackson tree model`, `@JsonInclude`, null 처리.

### 3.2 대량 데이터 적재(bulk load)
- **UPSERT 개념**: `INSERT ... ON DUPLICATE KEY UPDATE`(MySQL) / `MERGE` / `INSERT ... ON CONFLICT`(Postgres).
  어떤 UNIQUE 키로 충돌을 판정하는지가 전부다. → *"멱등한 적재"가 왜 재시도 안전성을 주는지.*
- **배치 크기(batch size)와 트랜잭션 경계**: 한 번에 몇 건씩 넣을지, 실패 시 어디까지 롤백되는지.
  → 검색어: `JDBC batch`, `rewriteBatchedStatements`, `chunk-oriented processing`(Spring Batch).
- **멱등성(idempotency)**: "같은 작업을 두 번 해도 결과가 같다"는 속성. 재개·중복 실행 설계의 핵심.

### 3.3 커버리지 알고리즘 — quadtree
- **왜 필요했나**: API가 "한 번에 N건까지만" 준다는 제약을 공간 분할로 우회.
- **개념**: 2D 공간을 4개 사분면으로 재귀 분할하는 트리. 밀도가 높은 영역만 더 깊이 쪼갠다.
  → 검색어: `quadtree`, `spatial indexing`, `recursion depth limit`.
- **주의할 트레이드오프**: 너무 잘게 쪼개면 API 호출이 폭증(비용·시간), 너무 굵으면 누락.
  깊이 상한·초기 셀 크기는 **실측으로 튜닝**해야 하는 값이다.

### 3.4 좌표·행정구역 데이터(지오코딩)
- **좌표계**: 위경도(WGS84), x=경도/y=위도 관례. bounding box = (minLng, minLat, maxLng, maxLat).
- **행정구역 코드 체계**: 법정동/행정동, 시도·시군구 코드가 기관마다 다르다(카카오 vs TourAPI vs 통계청).
  서로 다른 표기를 이어붙이려면 **매핑 테이블 또는 역지오코딩**이 필요하다.
  → 검색어: `reverse geocoding`, `법정동 코드`, `coord2regioncode`.

### 3.5 스키마 진화(schema migration)
- **하위 호환 마이그레이션**: 기존 행을 깨지 않고 컬럼을 추가하는 법(`DEFAULT`, NULL 허용).
  이번에 `content_id`를 NOT NULL→NULL로 완화한 이유를 이해할 것.
- **UNIQUE 제약과 NULL**: MySQL은 UNIQUE 컬럼에 **여러 NULL을 허용**한다(표준 동작). 이걸 알아야
  "content_id UNIQUE인데 카카오 행은 NULL 여러 개" 설계가 성립함을 안다. → *DBMS마다 다르니 확인 필수.*

### 3.6 Spring 실무 개념(내가 얕게 쓴 부분)
- **빈(Bean) 주입과 타입 충돌**: 같은 타입 빈이 둘이면 주입이 모호해진다(`@Qualifier`, `@Primary`).
  이번엔 그 충돌을 피하려고 카카오 `RestClient`를 빈이 아니라 생성자 안에서 만들었다.
- **`@RestControllerAdvice` 전역 예외 처리**: 서비스에서 던진 예외가 어떻게 HTTP 응답이 되는지의 흐름.
- **URL 기반 권한 부여**: `SecurityConfig`의 `requestMatchers(...).hasRole(...)` 한 줄이 컨트롤러
  애노테이션 없이도 권한을 거는 방식.

## 4. 실제로 쓸 때 주의할 점 (지뢰밭)

이번 구현에 **의도적으로 남긴 한계와 위험**을 솔직하게 적는다. 다음에 이걸 프로덕션에 쓰려면 반드시 본다.

### 4.1 이번 코드의 알려진 한계
- **체크포인트 없음 (재개 불가)**: 지금은 한 번에 끝까지 돈다. 쿼터 소진 시 중단은 하지만
  **다음 실행이 처음부터 다시 훑는다**. 업서트라 데이터는 안전하지만 API 호출이 낭비된다.
  → 실전에선 `(source, category, cell, page)` 커서를 DB에 저장하는 **체크포인트/재개**가 필수(Phase B).
- **동기·단일 스레드·블로킹**: 관리자 요청 하나가 수천 콜을 순차로 돌린다. HTTP 요청 타임아웃·커넥션에
  묶인다. → 실전은 **비동기 잡/스케줄러**(Spring Batch, `@Async`, 메시지 큐)로 빼야 한다.
- **지역 매핑이 best-effort**: 주소 문자열 파싱은 예외 케이스(2단계 시군구, 표기 변형)에서 깨진다.
  매칭 실패 행은 **그냥 버린다(skip)**. 손실률을 로그로 봐야 하고, 중요하면 역지오코딩으로 보완.
- **카테고리 매핑이 근사치**: 카페(CE7)를 음식점(39)에 억지로 합쳤다. 분류 정확도가 중요하면 코드 체계를
  재설계해야 한다.

### 4.2 외부 API를 다룰 때 공통 주의
- **이용약관·라이선스**: 수집·저장·재배포가 허용되는지 반드시 확인. 크롤링은 특히 회색지대
  (그래서 이 프로젝트는 크롤링을 주력에서 뺐다). 상용/포트폴리오 공개 시 더 민감.
- **키 노출 금지**: API 키는 `.env`·시크릿 매니저로. **소스·커밋·로그·URL에 절대 넣지 말 것.**
  (이번 코드도 키는 `${KAKAO_LOCAL_API_KEY}`로만 주입.)
- **쿼터 소진 리스크**: 무한 재귀·과도한 격자 세분화가 하루 한도를 순식간에 태울 수 있다.
  **상한(깊이·셀 수)과 리미터**를 반드시 걸고, 소량으로 스모크 테스트 먼저.
- **응답 변화에 대한 방어**: 외부 API는 예고 없이 필드·형식이 바뀐다. 파싱 실패가 전체 배치를 죽이지
  않도록 **건 단위 try/catch + 건너뛰기**로 격리.

### 4.3 대량 적재를 할 때 공통 주의
- **DB 부하**: 대량 INSERT는 락·인덱스 갱신·바이너리 로그를 유발. 운영 중 테이블에 돌리면 다른 쿼리가
  느려진다. → 배치 시간대·청크 크기·인덱스 전략을 고려.
- **중복 판정 키 설계가 전부**: UPSERT의 UNIQUE 키를 잘못 잡으면 중복이 쌓이거나 엉뚱한 행을 덮어쓴다.
  이번엔 `(source, external_id)`가 그 키. **키를 먼저 확정하고 코드를 짜라.**
- **부분 실패의 관측 가능성**: 몇 건 저장/몇 건 skip/몇 콜 소비를 **결과로 반환·로그**해야 나중에
  신뢰할 수 있다(이번 `SyncResult(saved, skipped, apiCalls, elapsedMs, quotaHit)`).

## 5. 한 줄 회고

이번 구현의 진짜 학습 포인트는 "카카오 API 사용법"이 아니라 **① 검증된 구조를 미러링하는 판단 ·
② API 제약(45건 상한)을 알고리즘(quadtree)으로 우회하는 발상 · ③ 업서트로 멱등성을 확보해
재시도를 두려워하지 않는 설계**였다. 세 가지는 어떤 외부 데이터 수집기에도 그대로 재사용된다.
다음 단계(B 체크포인트 · E 벤치마크)는 이 위에 "재개 가능성"과 "성능 근거"를 얹는 일이다.
