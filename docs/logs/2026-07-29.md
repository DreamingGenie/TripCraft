## 1. 기존 구조 재사용 vs 신규 작성의 경계

TourAPI 수집은 `client`(호출) · `service`(순회·업서트) · `client 리미터`(쿼터) ·
`controller`(관리자 트리거)로 나뉘어 있다. 카카오도 같은 뼈대를 그대로 따랐다.

- **재사용**: `AttractionMapper.insertAll`(멀티로우 + `ON DUPLICATE KEY UPDATE`),
  `system_config` 기반 일일 쿼터 카운트 패턴, `/api/admin/**` → `hasRole("ADMIN")` 보안 컨벤션,
  `SyncResult` 레코드 반환 형태.
- **신규**: 카카오는 인증이 쿼리 파라미터가 아니라 `Authorization: KakaoAK {key}` **헤더**라,
  헤더 없는 공용 `restClient` 빈을 재사용하면 안 됐다. 같은 타입(`RestClient`) 빈을 하나 더
  등록하면 기존 `TourApiClient`의 타입 주입이 모호해지므로, **별도 config 빈을 만들지 않고**
  `KakaoLocalClient` 생성자 안에서 전용 `RestClient`를 빌드했다(헤더 고정). 빈 충돌 회피 + 파일 수 절감.

## 2. 커버리지 전략 — rect 격자 + quadtree

카카오 category 검색은 지역명보다 **좌표 사각형(rect)** 검색이 강하고, rect당 결과가 **최대 45건**
(15건 × 3페이지)으로 잘린다. 그래서:

- 전국 bounding box(경도 124.5~132, 위도 33~38.7)를 0.5° 격자 셀로 순회.
- 한 셀에서 3페이지를 다 쓰고도 `is_end=false`면 = 45건 상한에 걸린 것 → **셀을 4분할해 재귀**
  (quadtree, 최대 깊이 4 ≈ 3.4km 셀). 바다·시골 셀은 1콜(page1 `is_end`)로 즉시 종료돼 낭비가 적다.
- 셀이 겹쳐 같은 장소가 여러 번 잡혀도 `UNIQUE(source, external_id)` 업서트가 idempotent하게 흡수.

## 3. 가장 성가셨던 부분 — 카카오 주소 → 우리 지역 코드

`attraction.sido_code`/`sigungu_code`는 NOT NULL이다. 카카오 응답엔 우리 코드 체계가 없고
`address_name` 문자열("서울 강남구 역삼동 …")만 있다. 두 가지 함정:

1. **시도 표기 불일치**: 카카오는 축약형("충북","경북","전북")을 쓰는데 TourAPI 공식명은
   "충청북도"·"경상북도"라, 접미사 정규화로는 화해가 안 된다. → 카카오 표기 → TourAPI `areaCode2`
   코드의 **명시적 별칭 맵**(17개, 축약·공식 표기 모두 수록)으로 해결.
2. **시군구 2단계**: "성남시 분당구"처럼 시/구가 쪼개지는 경우. → region2 단독 매칭 실패 시
   region2+region3 결합("성남시분당구")으로 한 번 더 시도. 그래도 실패하면 skip + 건수 집계.

이 부분은 Phase A의 best-effort다. 좌표 역지오코딩 보완은 후속으로 남겼다.

카테고리 매핑도 근사치다: `AT4→12`(관광지) `CT1→14`(문화시설) `AD5→32`(숙박) `FD6→39`(음식점)
`CE7→39`(카페를 음식점에 근사). TourAPI 콘텐츠 타입에 카페 전용 코드가 없어 39로 합쳤다.

## 4. 스키마 최소 변경 (v0.5 → v0.6)

A만 하더라도 카카오 행을 담으려면 스키마가 바뀌어야 해서, 그 최소분만 포함했다.

- `source ENUM('TOURAPI','KAKAO') DEFAULT 'TOURAPI'` — 기존 행은 디폴트로 자연 정합.
- `external_id VARCHAR(30)` — 카카오 place id. TourAPI 행은 NULL.
- `content_id`를 **NULL 허용**으로 완화 — 카카오 행엔 TourAPI contentid가 없다.
  MySQL UNIQUE는 다중 NULL을 허용하므로 기존 `uq_attraction_content_id`는 그대로 뒀다.
- `UNIQUE(source, external_id)` 추가 — 카카오 업서트 dedup 키.
- `attraction_detail_*`는 `content_id`(FK) 기반이라 카카오 행(content_id=NULL)은 상세를 안 갖는다.
  FK 정합성엔 영향 없음.

업서트 SQL의 `ON DUPLICATE KEY UPDATE`에 좌표·tel도 갱신 대상으로 추가했다(기존엔 title·addr1만).
재수집 시 카카오가 갱신한 좌표/전화가 반영되도록.
